# Staging deployment + monitoring runbook

Audience: the operator doing the first staging deploy. Everything here is a
command or a click; nothing is assumed. Cost: Render's smallest plans
(~$7–15/month total) + a managed Postgres.

## 1. Create the services

1. Push this branch to GitHub and connect the repo to Render (Blueprint
   reads `render.yaml`). It creates `scout-os-db`, `scout-os-web`,
   `scout-os-worker`, and the shared env group.
2. **Before the first deploy**, connect to the new database as Render's
   default user and run `scripts/render-db-roles.sql` (creates the
   least-privilege `wos_owner` / `app_user` roles; the app must never connect
   as the database owner — that role can bypass RLS).
3. Apply migrations as the owner role:
   `DATABASE_URL_OWNER=<owner-url> pnpm db:migrate`
   (0019 is the last applied file. 0020–0027 are proposals in
   `packages/db/proposed/` awaiting owner review; 0020–0023 are reviewed in
   `docs/plans/migration-review-0020-0023.md`. Do not set
   `WOS_DURABLE_EVENTS=1` until 0022 is adopted and applied.)
4. Set the secret env vars in Render (all `sync: false` in render.yaml):
   `DATABASE_URL` (app_user URL, on BOTH services), `ANTHROPIC_API_KEY`,
   `STRIPE_*`, `GOOGLE_CLIENT_*`, `SMTP_URL`, `MAIL_FROM`.
   `BETTER_AUTH_SECRET` and `WOS_SECRETS_KEY` are auto-generated by the
   blueprint. Back up `WOS_SECRETS_KEY` separately — losing it makes stored
   integration credentials unreadable.

## 2. Verify the deploy (in order)

| Step | Command / check | Pass |
|---|---|---|
| Health | `curl $URL/api/healthz` | `{"ok":true,...}` |
| Migrations | response has no 503; `schema_migrations` = 19 rows (more once proposals are adopted) | count matches |
| Live integrations | `node scripts/verify-live-integrations.mjs` with staging env | 0 FAIL |
| Mock mode off | `WOS_MOCK_MODE` is `0`/unset | healthz/UI show no MOCK |
| Sign-up flow | create account; verification email arrives (SMTP_URL set) | verified login |
| First task | ask the assistant something; approve a tier-2 action | task COMPLETED |
| Worker | approve anything; confirm it runs without a page open | result in Tasks |

## 3. Monitoring (minimum viable)

Render has no alerting; add one external monitor (Better Stack, UptimeRobot,
or a cron + curl anywhere):

- **Uptime check** on `/api/healthz` every 60s. Alert on non-200.
- **Degraded integrations**: alert if `degraded` is non-empty for 15 min
  (an integration's breaker is open in the web process).
- **Worker backlog**: alert if `queueBacklog` > 100 for 10 min (tasks and
  approval expiries are not running — the worker is down or stuck).
- **Logs**: point `OTEL_EXPORTER_OTLP_ENDPOINT` at a collector when one is
  chosen; until then, Render log retention + `LOG_LEVEL=info` is the record.
- **Dead letters**: Recovery page (`/orgs/<id>/recovery`) lists them;
  replay is one click. Check daily during the pilot.

## 4. Rollback

- **App**: redeploy the previous build in Render (instant).
- **Migrations**: every file since 0009 has a tested rollback in
  `packages/db/rollback/` (round-trip proven by `scripts/test-rollbacks.mjs`
  in CI). Roll back newest-first, then redeploy the matching app build.
- **Secrets rotation**: rotate `BETTER_AUTH_SECRET` (invalidates sessions,
  acceptable) or provider keys in the provider dashboards. `WOS_SECRETS_KEY`
  rotation needs re-entry of stored integration credentials.

## 5. What staging sign-off means

All of: section 2 green for 7 consecutive days, at least one real Gmail +
HubSpot + Stripe (test-mode) round trip per integration, zero unresolved
dead letters, and the security review items in
`docs/security/audit-2026-11-23.md` either closed or consciously accepted.
Then, and only then, the production conversation.
