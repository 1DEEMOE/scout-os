## Findings

### F1 — LOW: email verification was opt-in; default shipped unverified accounts
`requireEmailVerification` defaulted off "so existing deployments don't strand unverified users." For a product whose agents send email as the business, new deployments should default to verified accounts.
**Fix applied:** `render.yaml` now sets `WOS_REQUIRE_EMAIL_VERIFICATION=1` for new deployments. Existing local/dev flows are unchanged (the env var still controls it).

### F2 — LOW: `/api/healthz` was database-only plus the in-process breaker
The durable breaker state is per-tenant and correctly NOT exposed on an unauthenticated endpoint. But the health check gave no signal for the failure mode users actually feel first: the worker falling behind.
**Fix applied:** healthz now also reports `queueBacklog` (queued + retrying pg-boss jobs, an aggregate count safe to expose), alongside the existing per-process breaker list. Alert rule: backlog > 100 for 10 minutes, or any `degraded` entry for 15 minutes.

### F3 — LOW: rate-limit table is global, not per-tenant, and keyed by IP+path
Fine at current scale. At multi-replica scale behind a proxy, ensure `X-Forwarded-For` trust is configured at the edge (`WOS_TRUSTED_PROXY_HOPS` is already in render.yaml), otherwise all tenants share one bucket per proxy IP. Documented in the staging runbook.

### F4 — INFO: Better Auth `/api/auth/*` origin handling
The library performs its own origin validation against `baseURL`/`trustedOrigins`. `baseURL` is set from `BETTER_AUTH_URL`. No explicit `trustedOrigins` list is configured — acceptable while the app is single-origin; add `trustedOrigins` if a separate marketing/booking domain is ever pointed at the same backend.

### F5 — INFO: approval TTL wake-up relies on the worker being alive
`requestApprovals` enqueues a delayed run so expiry fires without user interaction. If the worker is down longer than the TTL, approvals expire late (on next worker tick), never early. Fail-closed — no action needed.

## What this review did NOT cover

- Live OAuth flows against real Google/HubSpot/Stripe apps (no credentials in this environment). Use `scripts/verify-live-integrations.mjs` on staging.
- Dependency CVE scan against a live advisory feed (no outbound audit API here; wired into CI as `pnpm audit --prod --audit-level=high`).
- Penetration testing of a deployed HTTP surface (nothing deployed).
- Model behavior under adversarial prompting at scale — the deterministic guardrails are covered by `packages/core/evals/`; model-quality evals (classification accuracy, plan helpfulness) need a live key and remain open.

## Bottom line

The auth/RLS/approval surface is enforced at three independent layers (DB constraints, policy engine, UI review rules) and the two auto-discovering test suites pass against a real database. The residual risks are operational (unverified live integrations, no external audit yet), not architectural.
